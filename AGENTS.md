# Backend instructions

Follow [shared repository rules](../../AGENTS.md). This submodule provides the Elysia API used by the extension, website account pages and desktop client (`/api/user`) and by the admin dashboard (`/api/admin`). See the [backend guide](../../docs/backend.md) for behavior and interfaces.

## Structure and conventions

- `src/server.ts` composes plugins and route modules; `src/main.ts` listens on the configured port. Put each resource's endpoints in `src/routes/` and register new modules in `server.ts`.
- `src/setup.ts` adds the Prisma client, locale helper, and current user to route context. `lang` (from `Accept-Language`) is the reader's language: reader routes list and search only novels and keywords named in it (`nameAr`/`nameEn`, novels also `descriptionAr`/`descriptionEn`); use `src/utils/translation.ts` for these translated fields. Aliases are named by `nameAr`/`nameEn` like keywords (at least one, each unique per keyword); keyword and alias descriptions use `descriptionAr`/`descriptionEn` on `KeywordVersion` (including the base) and `KeywordAlias`; versions’ descriptions are translated too, while chapters and replacements remain shared. `lib/keywords/descriptions.ts` applies partial locale writes and keeps the legacy `description` field for supported clients; shared-field writes are assigned by script when possible, otherwise request language. Translation merges keep each missing description language independently. Use it in routes that need those values. Auth guards and ownership checks live in `src/middleware/authorize.ts`.
- `src/lib/` contains database, Better Auth/session, email (Resend), storage, and AI code. Send email only through `sendEmail` in `src/lib/email/`. `src/lib/compat/` holds client-version and deprecation logic. `src/plugins/` holds Elysia plugins; `src/schemas/` and Elysia `t` schemas validate API input and describe responses. Use `HttpError` and the existing error handler for expected HTTP failures.
- `prisma/schema.prisma`, `prisma/migrations/`, and `prisma/seed/` own the database schema and data setup. Access the client through `@/lib/db` or the `prisma` route context. Use Prisma transactions for related writes. Serialize admin alias links and version range edits on their parent record; never absorb a versioned source into an alias and erase its history. Keyword and alias merges share `src/lib/keywords/merge.ts` (`absorb`, and `mergeTranslationKeyword`/`mergeTranslationAlias` for the reader and admin forms' translation links); keep one implementation and run a merge in the same transaction as the saved row's own write, before it, so the names it takes are free. Generate a development migration after schema changes; do not hand-edit an existing migration.
- Stored text is plain: `sanitize` trims and never HTML-escapes, and no client may insert stored text as HTML (`test/stored-text.test.ts` scans the extension, dashboard and website).
- A translation link (optional `translationKeywordId` on the keyword routes, `translationAliasId` on the alias routes, both portals) merges the row holding the saved row's other-language name into it and deletes it. It is an action, not a stored field: there is no column, a link naming a row that no longer exists is ignored so a replay succeeds, and style is never copied (the client's form sends the values it filled in). A client must not send the absorbed row's name in the same write; that row still holds it when `assertKeywordNamesFree`/`assertAliasNamesFree` run. Its refusals (`TRANSLATION_SELF`, `TRANSLATION_OTHER_NOVEL`, `TRANSLATION_OTHER_KEYWORD`, `TRANSLATION_SAME_LANGUAGE`, `TRANSLATION_HAS_VERSIONS`) are sync codes mirrored in the extension; readers may absorb only a row they could delete. `test/translation-link.test.ts` covers it with the live-database tests.
- Synced reader resources (keywords, aliases, versions, replacements, categories, natures, and file uploads) follow the [sync API](../../docs/backend.md#sync-api): creates require a client `id` (keywords also `versionId`) and a replay with the same creator and parent returns the stored row and skips every side effect (`src/lib/sync/replay.ts`); updates require `baseUpdatedAt` and check 404 → ownership (403) → staleness (409 `STALE_WRITE` with `current`, `src/lib/sync/precondition.ts`) → rules → atomic revision compare and write; a database trigger makes `updatedAt` strictly monotonic, including dashboard and bulk writes; updates are partial; deletes are unconditional. Every error on those routes carries a `code` from `src/lib/sync/error-codes.ts`; codes are a contract with the extension, never rename one, and pass them as `new HttpError({ code })` (stored as `errorCode`). Change a server rule and its extension mirror (`apps/extension/src/lib/offline/rules/validation.ts`) together. The change feeds (`src/routes/sync.ts`, `src/lib/sync/feed.ts`) come from Postgres triggers on `SyncChange`; trigger inserts hold a transaction-scoped advisory lock so `seq` is commit ordered. Full pulls use repeatable-read `/sync/snapshot/*` endpoints with a cursor from the same snapshot. A new synced table needs a trigger in a migration. `test/sync-*.test.ts` run against a disposable database with `make test-live`.
- `src/env.ts` validates server configuration. Add environment variables there and update `.env.example`; do not scatter direct `process.env` reads through application code.
- Lenses (see [Lenses](../../docs/backend.md#lenses)): change `lensBalance` only through `applyLensChange`/`withLensChange` in `src/lib/billing/ledger.ts`, always with a unique idempotency key (`test/billing-money.test.ts` scans for other writes). Money is integer micro-dollars and cents through `src/lib/billing/money.ts`; never `parseFloat` a price. Billing request status changes are compare-and-set on `PENDING`, approvals credit with `billing:<id>`, and billing and AI codes (`src/lib/billing/error-codes.ts`, `src/lib/ai/cloud/error-codes.ts`) are client contracts like the sync codes. New billing or cloud AI config keys go in `BILLING_CONFIG_KEYS` with a validator.
- Cloud AI (see [Cloud AI](../../docs/backend.md#cloud-ai)): the models are the `AI_Text_Model`/`AI_Image_Model` configs (OpenRouter IDs, chosen in the dashboard's Settings → AI; no model environment variable) and caps come from `AiFeaturePrice`; charges and refunds only through `src/lib/ai/cloud/actions.ts`; every provider request is an `AiCall`; never log prompts, page text, answers or images. Raw prompts/page text/provider responses remain transient; the explicit exception is published, validated `Chapter.context` JSON (summary, scene observations and lasting changes with bounded evidence) and its derived `ChapterMention` index. Feature keys are a contract with the extension: add one with a migration that seeds its record.
- Website sessions (see [Website sessions](../../docs/backend.md#website-sessions)): `web` sessions are read only from the cookie and only from the website's origin (writes also need `X-Storylens-Web: 1`); `bearer` sessions only from `Authorization`. Outside production, the default website origins `http://localhost:3000` and `http://127.0.0.1:3000` are accepted; additional ports need `WEBSITE_DEV_ORIGINS`. For local HTTP, set `WEB_SESSION_INSECURE_COOKIE=true` (the local `.env.example` does); production refuses this flag and accepts only `WEBSITE_URL`. Never return a web token in a response body, and never accept the cookie from other origins. Keep the website and API on the same hostname locally for `SameSite=Strict` cookies.
- Follow local module imports (`@/` for `src/`), resource naming, and explicit TypeScript types. Backend formatting is mixed; there is no backend Biome config, so avoid broad format-only changes.

## Permissions

Enforce access in the API; never rely on an extension or dashboard UI guard. See the [backend guide](../../docs/backend.md#portals-roles-and-permissions).

- One account can use both portals (`user` = extension, website account pages and desktop client; `admin` = dashboard): `isUser` + `userRoleId` and `isAdmin` + `adminRoleId`, plus an `isGuest` flag. Sessions store the `portal` they were issued for; build the current user with `toAuthUser(user, portal)`, which exposes only that portal's role. A role holds `Permission` rows; each permission key is a route's method and template (`GET /api/user/novels/:id`). `src/lib/permissions/sync.ts` creates rows for every non-public `/api/{portal}` route at startup, so a new route gets its permission automatically.
- Mount reader routes in `src/routes/user.ts` (`/api/user`) and dashboard routes in `src/routes/admin/` (`/api/admin`). In each module, `.use(setup)`, then the module's public routes, then `.use(authorize('user' | 'admin'))`: it rejects signed-out callers (401), sessions issued for the other portal, accounts without that portal's access, and missing route permissions (403). Nothing may live outside those prefixes except `/`, `/health`, `/docs` and the Better Auth `/auth/*` catch-all; `test/permissions.test.ts` enforces this.
- Add a new public endpoint only to `PUBLIC_ENDPOINTS` in `src/lib/permissions/catalog.ts` (reader guest/register/verify/login/providers/OAuth exchange, the website session's login/verify/OAuth exchange/logout, billing pricing, dashboard login). Give each new reader route a `USER_ENDPOINT_DESCRIPTIONS` entry and each dashboard route a `detail.summary`; decide its default access in `defaultAccessLevel` (GET = guest, writes = reader, `MODERATOR_ENDPOINTS` = moderator; dashboard routes go to the super admin).
- System roles (`super-admin`, `guest`, `reader`, `moderator`) are created by migration and referenced by slug (`SYSTEM_ROLES`); never delete them. Super admin always gets every admin permission. New guests get `guest`, verified registrations and Google sign-ups get `reader`.
- Inside reader routes, use `canModerate(authedUser)` (the `user:moderate` capability) instead of role checks, `assertOwnsResource` for reader-owned mutations, and `assertOwnsAnyOf` where several readers may change a row (aliases and versions: their own creator or the parent keyword's creator, decision D12). Readers fill a novel's `context` only while it is empty; moderators can replace it and edit existing version chapter ranges. Readers may choose an initial range while creating a keyword.
- `Keyword` and `KeywordAlias` store independent `wordVfx` enum values (`WordVfx`: default `NONE`; also `SPARKLES`, `HEAT`, `SHAKING`, `GLITCHING`, `GLARE`) and nullable `wordVfxColor` text (null inherits the word’s highlight color, otherwise `#RRGGBB`). Reader/admin writes validate optional values and preserve them on partial edits; downloads/sync include them. Alias VFX does not inherit the keyword’s or depend on `overrideStyle`. Preserve both fields when folding a keyword into an alias. Category `effect` remains only for supported legacy clients, with dated deprecation; new UI and rendering use category `wordVfx`/`wordVfxColor` defaults and independent word overrides.
- `Keyword` and `KeywordAlias` store `fuzzyMatchArabicCharacters` with default `true`. Reader and admin create/update routes accept the optional boolean; preserve it when folding a keyword into an alias. The extension alone applies the Arabic alif variant matching to page text. Keyword and alias names are stored without Arabic diacritics: every route that writes a name passes it through `cleanKeywordName` (`src/utils/arabic.ts`) before the name checks, and keyword searches strip the query the same way. Keep the diacritic set identical to the extension's `src/utils/arabic.ts`.
- Dashboard access is granted only through `POST`/`PUT /api/admin/users` or `make seed-dashboard-admin` (which grants it to `DASHBOARD_ADMIN_EMAIL`, keeping an existing account's password); there is no admin registration. Every account keeps at least one access, each with a role of its portal. Keep the dashboard guards: no changing one's own dashboard access or role, no self-deletion, never remove the last super admin, no deleting system roles or roles with users. Reader login and the OAuth exchange refuse accounts without `isUser`, and dashboard login refuses accounts without `isAdmin`.
- Better Auth handles OAuth only, at `/auth/*` (the Google redirect URI depends on it). Keep its credential, profile and linking endpoints in `disabledPaths` and `username`/`isUser`/`isAdmin`/`isGuest`/`userRoleId`/`adminRoleId`/`password` as `input: false`; never let a Better Auth endpoint set access.
- Email/password registration creates or upgrades an account only after `POST /api/user/auth/register/verify` accepts the emailed code; never create an unverified user or return a session from `/register`.
- Reader password and email changes require a registered account and an emailed code (`src/lib/auth/account-change.ts`); apply them only in the matching `/verify` route and update both credential stores atomically. Dashboard password changes (`PUT /api/admin/auth/password`) check the current password instead and sign out other sessions.
- `/health` and `/health/ready` are public and unauthenticated; never return error details, secrets, or user data from them.
- If an action's permission is unclear, ask before changing its default access.

## Backward compatibility and deprecation

Installed extensions and desktop clients stay on old releases for days or longer after the API deploys. Follow [API and data compatibility](../../docs/compatibility.md); these rules are enforced in review and by `test/deprecations.test.ts`. The offline-first release was a recorded, deliberate exception (decision D13): it changed the synced routes and raised both client floors in one coordinated release; later changes follow the rules below again.

- Change the API additively: new routes, new optional inputs, new response fields. Never rename, remove or retype a route or field in place, make an input required, tighten validation, or change error statuses or the `{ message }` shape for routes that shipped clients call. Keep `/api/user` and `/api/admin` as version 1; a `/v2` mount would duplicate permission keys and needs an agreed plan first.
- Deprecate before removing, always with a removal date: the `deprecated` route option (`{ deprecated: { since, removeAfter, replacement?, link? } }`, dates `YYYY-MM-DD`; it replaces the route's OpenAPI description and sends `Deprecation`/`Sunset`/`Link`), `deprecate(schema, …)` from `src/lib/compat/deprecation.ts` for request/response fields, and a one-line `@deprecated <what to use>. remove-after: YYYY-MM-DD` comment for code and Prisma `///` fields. Never write a bare `deprecated: true`. The test fails on undated, invalid or expired markers; when a date passes, remove the deprecated code (after checking the `DEPRECATED` logs) or move the date in a deliberate change. `make deprecations` lists them.
- Change the schema with expand → migrate → contract across separate releases: add nullable or defaulted columns, backfill, dual-write, switch reads, and drop the old column only after the API no longer exposes it and no supported client or offline sync payload sends it. Never rename or drop a used column in one migration.
- `MIN_CLIENT_VERSIONS` in `src/lib/compat/client-version.ts` is the oldest extension and desktop release served; the `client-version` plugin answers older `X-Client-Version` headers with 426 before routing and logs `OUTDATED`. Raise a floor only in the change that drops what those releases need, once logs show they are rare. Unversioned requests to the changed synced write routes also receive 426; unversioned web and other reader routes remain served. CORS exposes `Deprecation`, `Sunset`, `Link` and `X-Min-Client-Version`; add new client-readable headers to `exposeHeaders` in `src/plugins/cors.ts`.

## API and cross-submodule changes

The development OpenAPI UI is at `/docs` and the spec at `/openapi.json`; the extension's and dashboard's Orval configs consume the spec. Regenerate the extension client (`make orval`) after reader-API changes and the dashboard client (`make dashboard-orval`) after dashboard-API changes, and keep the dashboard's `src/lib/permissions.ts` in step with admin routes. ## Commands

From this directory, use `bun run dev`, `bun run typecheck`, `bun run test`, `make test-live` (with `TEST_DATABASE_URL` set to a disposable database: migrates it and adds the live-database tests), and `make deprecations` (lists deprecations and their removal dates; fails on expired or undated ones). Use `bun run db:generate`, `bun run db:migrate:dev`, and `bun run db:seed` for schema and seed work. `make help` lists Docker, migration, storage, and start targets. The `build` script currently generates the Prisma client, and `start` runs `src/main.ts`; do not assume a compiled production bundle.

`make db-reset` also runs the Prisma seed. Keep `make db-seed` safe to repeat or resume: reuse existing records and preserve edits, normalize keyword names with `cleanKeywordName`, and create missing chapter-zero versions using existing keyword IDs. Categories/natures and keyword-chapter links have no unique seed identity in the schema; chapters are unique by novel and number, so explicitly check for existing rows; `skipDuplicates` alone does not protect them. Legacy role mappings must reference the current category/nature data. `test/seed.test.ts` checks the mappings and, with live tests enabled, rehearses reset and repeated seeding in its own temporary database. The dashboard-only admin password reset remains intentional.

`test/helpers/browser-e2e-server.ts` is invoked by the umbrella's `scripts/lenses-e2e.mjs`. It requires a fresh `storylens_lenses_e2e_*` loopback database, applies migrations, seeds a fictional admin, disables external mail/provider credentials and injects deterministic AI replies. Never use it to start an ordinary development or production server. The umbrella `docs/lenses-local-e2e.md` describes the full browser rehearsal and cleanup.

Production runs under PM2. Deploy only with `make sync` (`pm2-stop`, `git pull`, `install`, `db-generate`, `db-migrate-deploy`, `build`, `pm2-restart`) and use the `pm2-*` Make targets rather than raw `bun`/`pm2` commands on the server. `src/scripts/` holds one-off scripts run through Make targets, such as `make seed-dashboard-admin` (grants `DASHBOARD_ADMIN_EMAIL` super-admin dashboard access) and `make set-review-version VERSION=x.y.z`, which `.github/workflows/set-review-version.yml` runs over SSH when the extension repo dispatches `extension-submitted`. The `review-version-watcher` cron in `src/plugins/crons.ts` runs `make sync` once the `Review_Version` config matches the published Chrome Web Store version; logic lives in `src/lib/review-version.ts`. Only after a successful sync does it run `make notify-dashboard`, which dispatches `backend-deployed` to `storylens-dashboard` using `DASHBOARD_DISPATCH_TOKEN` (`src/lib/dashboard-deploy.ts`); the dashboard's workflow then deploys it.

Keep this file and the [backend guide](../../docs/backend.md) current when backend rules, structure, commands, or interfaces change, following the root maintenance rule.

## Initial ranges and Word VFX

`POST /api/user/keywords` accepts optional nonnegative integer `startingChapter` (default 0) and nullable `endingChapter` (default null), bounded by PostgreSQL Int; reject end < start with `VERSION_RANGE_INVALID`. These set the initial version without granting readers later range-edit permission. Base versions may start above zero. New version creation orders all versions, including ones with a finite end; only close the previous range when open or overlapping, preserving explicit gaps. Keep extension validation and projection in step.

`Keyword.wordVfx` and `KeywordAlias.wordVfx` store the independent defaulted `WordVfx` enum (`NONE`, `SPARKLES`, `HEAT`, `SHAKING`, `GLITCHING`, `GLARE`) and nullable `wordVfxColor` text (`null` or a six-digit hex string); reader/admin creates and updates accept optional validated values, preserving existing ownership rules and partial writes. Reads, snapshots and change feeds expose them automatically. Unknown/missing read values fall back to None. Apply migrations `20261016154843_word_vfx` and `20261016163040_word_vfx_color` before the backend and regenerate API clients. Color writes are optional, null explicitly clears them, omitted partial fields preserve them, and malformed colors are rejected at the API boundary. The color migration preserves existing effects when converting the unreleased text fields to enum storage; `test/sync-migrations.test.ts` verifies it. The category `effect` field remains compatible for legacy clients with a dated deprecation; current UI/rendering ignore it. `test/keyword-options.test.ts` exercises defaults, replay, isolation, effects, ranges and permissions against a disposable database.


## Account color preferences

`routes/color-preferences.ts` exposes `GET /api/user/color-preferences/` (full account snapshot) and `PUT /api/user/color-preferences/:kind/:id` (`category` or `nature`, `{ color: "#RRGGBB" | null }`). Guests, readers and moderators receive both permissions; always derive `userId` from `authedUser`, never a request field. Only personal rows change; existing original category/nature writes stay moderator-only. A null color is an idempotent clear, including after lookup deletion. Per-color upserts use last applied write wins; separate rows avoid overwriting unrelated colors from other devices.

`UserCategoryColor`/`UserNatureColor` are account preferences with unique owner/lookup pairs and cascading user/lookup deletion. They use their own small full-snapshot sync, outside the shared catalogue's `SyncChange` feed, so private choices never appear in shared downloads. Apply `20261016145144_personal_lookup_colors` and `20261016150100_personal_color_row_ids` before deploying this API, and regenerate Prisma/prismabox and the reader client. The separate row IDs support prismabox; the owner/lookup pairs remain unique. `mergeGuestInto` carries synced guest colors into the member account while preserving the member's existing choices. `test/color-preferences.test.ts` checks permissions, account isolation, validation, clears and guest adoption against a disposable database.

## Shared chapter covers

`routes/chapter-covers.ts` serves `/api/user/chapter-artwork/:novelId/:chapterNumber` (and the dated `/chapter-covers` compatibility adapter): GET reads public image metadata and generation status; POST `/claim` reserves a missing cover or accepts optional `regenerate: true` for publisher/moderator replacement; PUT completes the caller's token with an image uploaded by that account; DELETE `/claim` releases only that account's token. Guests read; reader/moderator roles may claim, publish and release. Artwork belongs to the canonical `Chapter`, unique by novel/chapter number; detected chapters are created on demand. Serialize claims with a transaction advisory lock. Tokens never appear in public reads; leases expire after 30 minutes, completed covers are reused unless explicitly regenerated, and same-file publish replay is idempotent. Replacement claims retain the existing image and report `generating: true`; token ownership/expiry protects both replacement and cancellation. Cascading novel deletion removes covers; deleted images become missing covers.

Apply migration `20261016180556_chapter_covers`; it also seeds the `chapter_cover` AI feature (3 lenses, 180,000 prompt characters, 1,600 brief tokens). `/ai/images` accepts it alongside `character_image`, with optional up-to-eight HTTP(S) `referenceImageUrls`. Covers use scene-specific system rules, a longer brief and 16:9 landscape composition; character portraits keep their existing rules and ratio. Both get one attempt and the same charging/refund safeguards. Forward references as OpenRouter `input_references`; never fetch them on the API server or retain prompt/reference contents in usage logs. `test/chapter-covers.test.ts` and the image cases in `test/ai-cloud.test.ts` use a disposable database.

## Chapter context and artwork

`Chapter` is canonical by `(novelId, number)`, including automatically detected chapter zero. It stores `context` JSON and an `imageId` relation to File; there is no description column or ChapterCover table. Migration `20261017000000_chapter_context` merges duplicate chapters while retaining keyword links, moves old descriptions to `context.summary`, and copies every cover image/owner/active reservation before dropping the old table. The physical consolidation is explicitly requested; existing cover endpoints stay compatible as dated adapters to `/chapter-artwork` (remove-after: 2027-04-30). Legacy chapter description inputs map to summary without deleting scene context. Ordinary chapter selects/schemas must exclude context bodies and all lease fields; use `chapterPublicSelect` and the public `ChapterPlain` export from `lib/db`, never the generated private Chapter schema.

`/chapter-context/:novelId/:chapterNumber` reads only that chapter and recently absent entity metadata. Claim/publish/release use an owned 15-minute lease and source SHA-256; identical content reuses a saved context unless an authorized manual claim supplies `regenerate: true`. `onlyIfMissing: true` takes precedence over regeneration. Publication under a matching live lease replaces even same-hash context; completed writes remain idempotent. Automatic claims set `onlyIfMissing: true`; under the claim lock, any saved valid context returns ready regardless of its hash, preventing concurrent automatic replacement. Registered readers create missing contexts; only the publisher or a moderator can replace an existing hashed context. `lib/chapter-context/schema.ts` validates bounded JSON, canonical keyword IDs, scenes, references and lasting changes; the extension carries an equivalent schema. Publishing replaces the derived mention index in the same transaction. Context and artwork are online resources outside the offline snapshot/feed.

The separate GET `/continuity` is called only while preparing images or copying image prompts. It returns the exact available N−2…N+2 contexts, latest earlier mentions for requested entities and the newest earlier value per lasting-state field (including explicit null clears). Never apply future state to earlier scenes. `ChapterMention` retains history permanently; the recently absent list derives `currentChapter-lastMentionedChapter` and expires at 15 without deleting keywords or historical state. Do not increment counters on page visits. Context generation itself reads no neighboring contexts. `test/sync-migrations.test.ts` rehearses artwork/description/lease/link preservation and physical table/column removal. The `chapter_context` Cloud feature uses the normal billing/refund/correction machinery; migration seeds its editable price and limits.

Cloud generation controls are validated Config keys `AI_Reasoning_Effort` (default `auto`), `AI_Reasoning_Token_Allowance` (0–32768, default 4096), and `AI_Image_Quality` (default `auto`). Read them once per action and pass them through `ChatInput`/`ImageInput`, including the image-brief chat and `ai_smoke.ts`. `generation-settings.ts` resolves unsupported saved options to Auto using the cached model catalog; mandatory thinking cannot receive none. The provider adds the allowance to the feature completion cap when thinking is enabled; thinking and answer share that combined budget and thinking tokens remain billed/recorded as output. Exclude reasoning text from returned answers. Model metadata augments the admin catalogue additively; if public metadata is unavailable generation still forwards explicit settings. No reader request can override admin generation settings.


Available lens stock is the Config row `AI_Lens_Balance` (whole lenses, 0–999,999,999; missing/invalid means zero), maintained manually with the dashboard’s dollar converter. `lib/billing/inventory.ts` serializes its edits, deletion and deductions with a transaction-scoped advisory lock. Deduct on approved sales and dashboard gifts only, in the same transaction as the reader ledger credit and request status change; skip deductions on idempotent gift replays. Readers’ AI spending/refunds, trial gifts and audited balance corrections leave stock unchanged. Insufficient stock returns 409 `AI_LENS_BALANCE_TOO_LOW` and rolls back every related write. The optional `baseUpdatedAt` on Config PUT rejects stale stock replacements with 409 `CONFIG_STALE`; current dashboard editors send it, while older clients remain compatible. No new database migration is required.

Admin novel inspection has `GET /api/admin/novels/:id/chapters` (paginated, sorted by chapter number, public chapter fields and artwork only) and `GET /api/admin/novels/:id/chapters/:chapterId` (scoped chapter artwork and validated structured context). Chapter lists omit context bodies and both endpoints omit private generation reservations. Each route has its own admin permission, granted to the super admin through normal permission sync.


Keywords and aliases have nullable `mainThemeColor`, added by the additive `main_theme_color` migration. Reader and admin create/update accept an optional `#RRGGBB` value or null (clear), independent of Word VFX and alias `overrideStyle`. Omitted fields preserve existing values for old clients. Existing ownership and permission guards apply. Keyword-to-alias conversion preserves the color; translation links keep the surviving record’s shared color. Prisma plain models expose it through keyword/alias responses, admin profiles, snapshots and change feeds; the compact admin keyword response exposes it too. A keyword’s override applies across chapter versions and is inherited by aliases unless they set their own color; the displayed lookup color (category, or nature when swapped), including its personal preference, is the fallback. No new route, permission or offline database version is required. Regenerate both reader and dashboard clients after schema generation.


Category VFX defaults use `KeywordCategory.wordVfx` (WordVfx enum, NONE) and nullable six-digit-hex `wordVfxColor`, added by `20261017213830_category_word_vfx`. Existing categories start at NONE/null; do not revive deprecated `effect` values. Moderator reader creates/partial updates accept both optional fields and replay checks include supplied VFX values. Category responses, embedded keyword styles, snapshots and feeds include them. `PUT /api/admin/keyword-categories/:id` edits only VFX/tint under its own admin permission and requires `baseUpdatedAt`; stale writes return 409 with current values. The extension uses a word’s non-None effect/tint first, otherwise the category resolved for its chapter/alias style. Aliases do not inherit the parent word’s effect. Existing appearance visibility and motion protections apply. Deploy the migration and regenerate both clients together; older clients retain their existing API fields.

Migration `20261017214616_glare_word_vfx` additively extends `WordVfx` with `GLARE` for keyword, alias and category values. Reader/admin schemas use the generated enum, preserving optional partial writes and existing permission/replay rules. The deprecated category `effect` input keeps its old choices; new clients use `wordVfx`. Glare renders as a diagonal white glow sweep in the extension and does not use a custom tint. Older readers safely ignore unknown effects.


Lookup deletion accepts optional UUID query `replacementId` on the existing moderator DELETE `/api/user/keyword-categories/:id` and `/keyword-natures/:id` routes. `lib/sync/delete-lookup.ts` locks source/destination rows in ID order, validates same-type existence, moves every `KeywordVersion`/`KeywordAlias` foreign key and deletes the source in one transaction.
